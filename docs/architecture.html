RAGForge Explained

What the app does, what runs in the background, and how to talk about it. Written for someone who needs to explain the project without having watched it being built.

I have an interview soonStart with the 30-second pitch, then the questions and answers. I want to understand itRead from the top. Each part builds on the one before. I want to see it workExperiments that make the background work visible.

01What RAGForge is

AI chat tools know a lot about the world and nothing about your files. Ask one about your resume, your company handbook or last year's contracts and it will guess, or invent something confident. RAGForge fixes that. You give it your documents. When you ask a question it first looks up the relevant passages in your documents, then hands those passages to an AI and says "answer using only this". The answer comes back with numbered sources you can click.

That pattern has a name: RAG, Retrieval-Augmented Generation. Retrieval is the lookup. Generation is the AI writing the answer. Augmented means the lookup results are added to the question.

RAGForge is a complete, self-hosted product around that idea:

  • You upload any number of files (PDF, Word, Markdown, text, or a web page address). They are indexed in the background, so the page never freezes.
  • You ask questions in a chat and get cited answers.
  • Other AI tools can use your knowledge base too (Claude Code, Claude Desktop, Cursor) through a standard called MCP, with keys you control.
  • It runs on your own computer, with a local AI (Ollama) if you like, so documents never have to leave the machine.
  • You install it with one command (npm install -g @masterdeepak15/ragforge) and run it with ragforge start.
The 30-second pitch “RAGForge is a self-hosted knowledge base. You upload your documents, it indexes them in the background, and then you can ask questions and get answers with clickable sources, or let tools like Claude Code search the same documents over MCP. It combines meaning-based and keyword search, runs fully locally with Ollama if you want, and installs with a single npm command.”

02The big picture

Everything RAGForge does runs inside one Node.js program (the server). That program serves the web page, answers API requests, runs the background indexing, talks to AI providers and speaks MCP. It keeps its data in one SQLite file plus a folder of uploaded files. There is no separate queue server, no separate vector database, no Kafka.

What is actually running in the background

The ragforge command itself is not a background program. It runs, does its job (start, stop, check, configure) and exits.

03Words you need

These come up in every explanation. Learn them in this order.

Chunk

A document is too big to hand to an AI whole, and too big to search as one block. So it is cut into pieces of about 1,000 characters. Each piece is a chunk, and chunks are what get searched.

Here: each chunk overlaps the next by 200 characters so a sentence on a boundary is not lost.

Embedding (vector)

A list of a few hundred numbers that captures what a piece of text means. Texts with similar meaning get similar numbers, even with different words.

Here: the model nomic-embed-text makes 768 numbers per chunk.

Cosine similarity

A score from 0 to 1 for how close two embeddings point. 1 means the same meaning, near 0 means unrelated. It is how “the meaning of your question” is compared to “the meaning of each chunk”.

Here: the Playground shows this as Similarity.

Keyword search (BM25)

Classic word matching, ranked by how rare and how frequent the words are. Finds exact names, codes and terms that meaning-based search can miss.

Here: SQLite's built-in full-text index, FTS5.

Hybrid search + RRF

Run both searches, then merge the two ranked lists. Reciprocal Rank Fusion gives each result points for its position in each list (1st place earns the most) and adds them up.

Here: meaning counts 70%, keywords 30%, adjustable per knowledge base.

LLM

The large language model that writes the answer. It only sees what the prompt contains, which is why retrieval matters.

Here: Ollama, OpenAI, Gemini, Anthropic or Groq.

Knowledge base

A named collection of documents searched together, like a folder with its own index and search settings.

Each one has its own vector table.

SSE (Server-Sent Events)

A one-way live connection from server to browser. The server pushes small messages; the browser listens. Simpler than WebSockets when only the server needs to talk.

Here: indexing progress, and the words of an answer as they are written.

MCP

Model Context Protocol: a standard way for AI tools to call outside tools. RAGForge offers four read-only tools, so Claude Code can “search my knowledge base” just as you would.

Here: POST /mcp with an API key.

JWT and API key

Two kinds of pass. A login token (JWT) proves a person signed in. An API key (rf_…) lets a program, such as an MCP client, in without a person.

Here: tokens last 7 days; keys can be limited and revoked.

04Upload and indexing: the background work

This is the part that is invisible when you use the app, so it is worth knowing step by step. The key idea: uploading is fast and indexing is slow, so they are separated. The upload request only saves the file and writes a to-do item. A worker picks up that to-do item later.

Step by step

  1. Upload. Files up to 50 MB go as one streamed request. Bigger files use a resumable upload: the browser sends the file in pieces, and if the connection drops it continues from where it stopped. Either way the file is streamed straight to disk, never held whole in memory, which is why there is no size limit.
  2. Duplicate check. The server computes a SHA-256 fingerprint of the content. The same file uploaded twice to one knowledge base is recognised and not indexed again.
  3. A document row and a job row. The document gets status pending. A row in ingestion_jobs gets status queued. The queue is a database table, so it survives restarts.
  4. A worker claims the job. Two worker loops run (the setting INGEST_CONCURRENCY). Each polls every half second, or is woken immediately when a job is added. Claiming is one guarded SQL update (“set running where status is queued”), so two workers can never take the same job.
  5. Extract text. PDFs go through unpdf, Word files through mammoth, web pages are fetched and cleaned (cheerio and Readability), and Markdown or text files are streamed in pieces of about 2 million characters so even a gigantic file uses bounded memory.
  6. Chunk. A recursive splitter tries to cut at paragraph breaks first, then line breaks, then sentence ends, then commas, then spaces, so chunks end at natural places.
  7. Embed in batches of 32. Each batch goes to the embedding provider. A rate-limit or temporary error is retried with growing delays.
  8. Store each batch immediately. The chunk text goes into document_chunks, the vector into that knowledge base's own vector table, and a database trigger adds the text to the keyword index. Storing as it goes keeps memory flat and makes progress real.
  9. Tell the browser. After each batch the worker publishes a progress event. The server relays it over SSE, and the progress bar moves.
  10. Finish. Document ready, job done, a “ready” event is sent. From now on this document is searchable.

The two small state machines

A document and its job each move through a few states. Knowing them lets you explain what “Failed” and “Retry” mean.

What a chunk looks like

What can go wrong, and what the app does

SituationWhat happens
The AI provider says “slow down” (HTTP 429) or has a hiccupThe batch is retried with growing delays. The queue slows down instead of failing.
No text in the file (empty, or a scanned PDF with no text layer)Fails at once with “No extractable text”. Retrying cannot help, so it does not retry. There is no OCR.
No embedding provider set up, or one that cannot embed (Claude, Groq)Fails at once with a message that names what to add.
You changed the embedding model after indexingFails with a clear message. Vectors from different models are not comparable, even if they have the same length, so mixing them would silently give bad answers.
The server is stopped or crashes in the middle of a jobOn the next start, jobs still marked “running” are put back in the queue. A job that already used all 3 attempts is failed instead, so a file that crashes the server cannot cause an endless restart loop.
You cancelA running job is told to stop (an abort signal checked between batches). The half-stored chunks are removed.
You retry a failed documentThe old partial chunks are deleted first, so the run starts clean and re-running is always safe.

05Asking a question

When you type a question in Chat, three things must happen: find the right passages, build a prompt, and stream the answer back. The knowledge base chosen for that chat decides which documents are searched. A chat set to “None” skips the search entirely and the AI answers from general knowledge, which is why the app now warns you about it.

How the best passages are found

The merge, with real numbers

Each result earns weight ÷ (60 + rank) points from each list it appears in. The 60 is a standard constant that keeps first place from running away with the score. Four passages, for example:

PassageRank in meaning searchRank in keyword searchPoints
A1st3rd0.7÷61 + 0.3÷63 = 0.0162
B2nd1st0.7÷62 + 0.3÷61 = 0.0162 (just behind A)
C3rdnot found0.7÷63 = 0.0111
Dnot found2nd0.3÷62 = 0.0048

A passage that appears in both lists beats one that is only first in a single list. That is the whole point of hybrid search. It also explains why those tiny numbers (about 0.016) appear as the “score” of results. They are rank points, not similarity.

Why “whatware” found somethingMeaning embeddings rate almost any two texts around 0.4 similar, so a nonsense word still lands near something. The fix is the minimum similarity setting (default 0.3, try 0.45 to 0.5 for nomic-embed-text). Passages below it are dropped unless they contain the exact words searched for.

The prompt the AI sees

You are a helpful AI assistant with access to a knowledge base. Answer clearly and concisely.

Use the following context to answer the user's question. Cite sources with [N] notation:

[1] Deepak_Resume.pdf
…text of passage 1…
---
[2] Deepak_Resume.pdf
…text of passage 2…

(then the earlier messages of this chat, then your new question)

The AI writes “…at Ador Powertron [1]”. The page turns each [1] into a button that opens the exact source passage. The model never needs to be trusted to remember your documents: it is shown the relevant parts every time.

Per-knowledge-base search settings

Passages per search, keyword search on or off, the two weights and the minimum similarity are stored per knowledge base (as JSON in the retrieval_settings column). The Playground, Chat and MCP all read the same settings, so tuning once changes how every one of them answers. Anything a caller sends explicitly, such as an MCP top_k, wins over the saved value.

06Other AI tools over MCP

MCP lets Claude Code, Claude Desktop or Cursor use RAGForge as a tool. The tool is read-only: it can look things up and never change anything.

“There are many knowledge bases, how does it pick?”

  • The AI first calls list_knowledge_bases and reads each name and description. The tool descriptions tell it to do exactly that. So give every knowledge base a one-line description.
  • It then passes the id of the one that fits to search_knowledge. If it passes none, all knowledge bases the key allows are searched and the results are merged by score.
  • You decide what it can see: ragforge mcp add claude-code --kb "HR,Legal" creates a key limited to those two. For a hard split, register one server per knowledge base: --name hr-docs --kb HR, --name legal-docs --kb Legal. The AI then sees two tools and picks by name, much like choosing in the chat screen.

09The screens

The web app is a React single-page app built with Vite and styled with Tailwind and accessible Radix components. In production the same Node server serves the built files, so there is only one thing to run.

How it stays live. Server data goes through TanStack Query, which caches and refreshes it. On a knowledge base page the browser also opens one SSE connection. When a progress or ready event arrives, the matching queries are refreshed, so progress bars and statuses change on their own.

10The command-line package

The ragforge command is what makes this installable by anyone. It is published to npm as @masterdeepak15/ragforge. One file contains the command, the whole server and (beside it) the built web app, so installing it gives you everything.

What ragforge setup does

  1. Asks where to keep data, which database file, which port, and who may connect (default: only this computer).
  2. Generates a random login secret and an encryption key and saves them in config.json (readable by you only).
  3. If Docker is running, offers to run Ollama in a container, bound to 127.0.0.1, with models stored in your data folder. It picks a chat model by your RAM (llama3.2:1b under 8 GB, llama3.2:3b up to 32 GB, llama3.1:8b above) and asks before downloading. Without Docker it says so and offers other routes.
  4. Creates the database and writes the Ollama provider into it, so the first start already works.

How it controls the background process

  • start launches the server detached (no window) and waits for a healthy answer, so “running” really means running. If it dies at once, the log's last lines are shown.
  • The pid file stores the process id and the start time. After a reboot the same number may belong to another program, so a pid file older than the last boot is treated as stale and never used to kill anything.
  • stop asks the process to end, waits, and forces it only if needed.
  • service install makes ragforge start run when you log in: a per-user “run at login” entry on Windows (no administrator rights; a first attempt with Task Scheduler was refused by Windows for normal users), a launch agent on macOS, a systemd user service on Linux.
  • mcp add creates an API key, then edits the AI tool's own configuration (merging, with a backup, and refusing to touch a file it cannot parse).
  • doctor checks Node, settings, data folder, port, Docker, Ollama and its models, and says what to do.

12Problems we hit, and how they were solved

Stories like these are the most convincing thing you can tell in an interview, because they show how you debug.

PDFs from the real world would not index

The first PDF library failed on valid files with the error “bad XRef entry” on the current Node version. The fix was to replace it with unpdf and test with real PDFs generated in the test suite. Lesson: a dependency that works in a demo can fail on real input, so test with real files.

Uploads over 1 MB failed with “413”

The upload plugin had a hidden default size limit of 1 MiB, which contradicted the “no limits” promise. The fix was an explicit unlimited setting plus a test that uploads a large file.

The AI answered, but nothing appeared on screen

The chat page tried to update an assistant message that had never been added to the list, so the answer was written to nothing. Found by writing a test that streamed a reply and looked for the text. Related fix: error events from the provider were ignored, so a failure looked like silence. They are now shown.

The AI ignored the documents

Two separate causes. First, the chat route passed the raw database row to the chat service, so the provider's API key and chosen model never arrived (the fields are snake_case in the database and camelCase in code). Second, a chat created with “None (general chat)” never searched anything. Fixes: map the fields properly, let a chat's knowledge base be changed, warn when a chat has none, and preselect one for new chats.

Provider setup “did not work”

The form sent field names the server did not expect, there was no validation, and no real connection test. Fix: rewrite the endpoints with validation, a real authenticated test request, sensible defaults, and a UI that shows why something failed.

Setup kept sending you back to the setup page

The app read “is it set up?” once at startup and never again, so after you created the admin it still believed it was a fresh install. Fix: the wizard refreshes that status before leaving, and the server returns the new user so the wizard can sign in directly.

Reloading a deep link gave a 500 error

The static file plugin was configured in a way that broke the “serve the app for any unknown page” fallback. Found in a real browser (not by unit tests), fixed and covered by a test.

A crash could restart-loop the server forever

If a file exhausted memory, the job stayed “running”, restart put it back, and it crashed again. Fix: recovery counts attempts and fails a job that already used them all.

Windows refused the “start at login” task

The obvious approach, a scheduled task at logon, needs administrator rights, which a normal user does not have. It only showed up when run for real, because the unit tests used a fake shell. The fix was a per-user entry in the “run at login” list. A related bug: backslashes in the registry path were silently dropped by JavaScript string rules, and the test had the same mistake, so both agreed and both were wrong. Lesson: tests that copy the code's assumptions prove nothing, so run it for real.

13See it with your own eyes

You will explain this better after watching it. Each experiment takes a minute or two.

  1. Watch indexing happen. Open a terminal and run ragforge logs -f. Upload a PDF in the browser. You will see requests arrive, then the worker busy. In the page, watch the Processing table: the stage changes (loading, chunking, embedding) and the bar fills.
  2. See the chunks. Open the document in the knowledge base and use the chunk inspector, or use the Playground to search and look at the passages that come back.
  3. See why hybrid search exists. In the Playground search for an exact word from a document, then for a paraphrase. Turn “keyword search” off and repeat.
  4. See the minimum similarity. Search for an unrelated word. Raise Min similarity to 0.5, run again, and the results disappear.
  5. Break it on purpose. Run docker stop ragforge-ollama, upload a file, and watch it retry and then fail with a clear message. Run docker start ragforge-ollama and press Retry.
  6. Prove it survives a restart. Upload a large file, run ragforge restart while it is indexing, and watch it resume from the queue.
  7. Use the MCP tools. After ragforge mcp add claude-code, ask Claude Code something that needs your documents and watch it call list_knowledge_bases then search_knowledge.
  8. Look at the data. Run ragforge status to see where the files are, then open the database file with any SQLite viewer and look at documents and ingestion_jobs.

The 30-second pitch

Say“RAGForge is a self-hosted knowledge base. You upload documents, it indexes them in the background, and you ask questions and get answers with clickable sources. Other tools like Claude Code can search the same documents over MCP. It combines meaning and keyword search, runs fully locally with Ollama if you want, and installs with one npm command.”

The two-minute walkthrough

Say“There are two flows. Indexing: when you upload a file the server saves it and puts a job in a queue stored in the database, then returns immediately. A background worker takes the job, extracts the text, cuts it into overlapping chunks, turns batches of chunks into embeddings with the chosen AI model, and stores the text, the vectors and a keyword index. Progress is pushed to the browser over server-sent events. If the server restarts, unfinished jobs go back in the queue. Asking: the question is embedded with the same model, then I run a vector search and a keyword search in parallel and merge them with reciprocal rank fusion. The best passages go into the prompt, the model streams the answer, and the sources are returned so each citation is clickable. The same retrieval is exposed through a stateless MCP endpoint with scoped, hashed API keys. Around that there is a CLI that sets everything up, including a local Ollama in Docker, and manages the process.”

Questions you may get

What is RAG, and why not just paste the document into the AI?

A document can be larger than the model's context window, and pasting everything every time is slow and expensive. RAG finds only the few relevant passages and sends those, so answers stay grounded in the documents and the cost stays small. It also gives you citations.

Why hybrid search?

Meaning search handles paraphrases but can miss exact names, product codes and rare terms. Keyword search is the opposite. Merging both with reciprocal rank fusion, a rank-based method that needs no score normalisation, gives better results than either alone.

How do you store and search vectors without a vector database?

SQLite through libSQL has a vector column type and a cosine-distance function. Each knowledge base has its own table, and search is an exact scan. I measured the database's index option and it inserted far more slowly, so I chose the exact scan: about 110 ms for 30,000 chunks, always correct. Above roughly 100,000 chunks per knowledge base I would move to Postgres with pgvector.

How do you handle very large files?

Uploads are streamed to disk, with a resumable path above 50 MB. Indexing streams the text in segments and embeds and stores in batches of 32, so memory stays flat no matter the size. Progress is real because each batch is stored as it is finished.

What happens if the server crashes in the middle of indexing?

The queue is a database table. On start, jobs left “running” are re-queued. Re-running is safe because a run deletes the document's earlier chunks first. A job that has already used all its attempts is failed instead, so a file that crashes the process cannot cause a restart loop.

Why server-sent events instead of WebSockets, Kafka or MQTT?

The traffic is one-way, server to browser, and everything runs in one process. SSE is built into browsers and needs no extra service. The event bus is an interface, so for several servers I could swap in Redis or NATS. Kafka would be heavy infrastructure for a self-hosted single-node tool.

How do you stop the AI making things up?

The prompt tells it to answer from the supplied passages and cite them, and a minimum-similarity threshold keeps unrelated passages out. It reduces the problem but cannot remove it, which is why every answer shows its sources so a person can check them.

How is the MCP endpoint secured?

Every request carries an API key. Only its SHA-256 hash is stored. Keys can be limited to chosen knowledge bases, are rate-limited to 60 requests a minute, and can be revoked instantly. The tools are read-only, and every tool re-checks the key's scope.

How are provider API keys stored?

Encrypted with AES-256-GCM using a key from the environment, which the setup command generates randomly and stores in a file readable only by the user.

What if you change the embedding model later?

Vectors from different models are not comparable, even if the length matches. The knowledge base records its model and indexing refuses a different one with a clear message, rather than silently producing bad search results.

How did you test it?

Test-driven: roughly 760 automated tests across the server (about 310), the web app (about 230) and the command line (about 220), plus browser end-to-end tests. They include real processes (start, stop, crash handling), a scripted fake Docker, and real file-based databases. Beyond that I ran the real thing in a browser and found bugs that tests had not, such as the deep-link error and the Windows autostart permission problem.

What was the hardest bug?

Pick one story from section 12. A good one: “answers never appeared”, because the symptom (blank chat) and the cause (updating a message that was never added) were far apart, and it was found by writing a test that reproduced the symptom first.

How would you scale it?

Move the database to Postgres with pgvector and an HNSW index, replace the in-process event bus with Redis or NATS, and run several stateless API servers and several workers pulling from the shared queue. The code already separates those parts behind interfaces.

What are its limits?

Scanned PDFs have no OCR. One SQLite file means one machine. There is one admin account and no multi-user management yet. Prompt injection from document content is only partly mitigated. Small local models can ramble. I can say what I would build next for each.

What would you improve next?

OCR for scanned files, a re-ranking step after the merge, a hardened Postgres mode, multi-user roles, and answer-quality evaluation with a set of test questions.

15Map of the code

Four packages in one repository. When someone asks “where is that?”, this is the answer.

WhereWhat is there
packages/server/src/index.tsBuilds the server: plugins, routes, the worker, the event bus, and starts listening.
services/ingestion.handler.tsThe indexing pipeline (sections 4): load, chunk, embed in batches, store, report progress.
queue/job-queue.ts, queue/worker.tsThe persistent job queue and the worker loops with retries and crash recovery.
core/ingestion/Text extraction for each file type and the recursive chunker.
core/retrieval/hybrid.retriever.tsQuestion to passages: vector search, keyword search, rank fusion.
core/vector/, core/search/fts.tsVector tables with the cosine scan, and the keyword index.
core/providers/One adapter per AI provider, the factory, the connection test, encryption and retry.
services/chat.service.ts, routes/chat.routes.tsPrompt building, streaming the answer, citations, chat sessions.
mcp/The MCP endpoint, its four tools, and the rate limiter.
auth/api-keys.tsCreating, hashing and checking API keys.
services/retrieval-settings.tsPer-knowledge-base search settings.
db/connection.tsOpens the database and creates or upgrades every table.
packages/web/srcThe React app: pages/, features/ by area, components/ui/, lib/ for the API client and uploads.
packages/cli/srcThe ragforge command: setup.ts, runtime.ts (start and stop), docker.ts, mcp-command.ts, service.ts, uninstall.ts, doctor.ts.
packages/sharedTypes and schemas used by both server and web.
